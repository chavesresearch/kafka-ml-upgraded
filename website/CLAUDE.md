# website — instructions for AI assistants

The Kafka-ML docs + SDK reference + interactive showcase site, built
with Docusaurus 3 (TypeScript config) and deployed to GitHub Pages via
`.github/workflows/website.yml`. A from-scratch addition (2026-08) - no
prior docs site existed anywhere in this repo before this.

## Stack

- Docusaurus 3.10 (`classic` preset), TypeScript config
  (`docusaurus.config.ts`, `sidebars.ts`, `sidebarsSdk.ts`)
- pnpm 11 / Node 22, own `package.json`/`pnpm-lock.yaml` - nothing else
  in this repo shares a `package.json`, and this stays consistent with
  that (no workspace/monorepo tooling introduced for one more package)
- `recharts` for the showcase's simulated-metrics charts - reused
  because `frontend/` already standardized on it, not picked
  independently
- No diagramming library (`reactflow`/`mermaid`/`d3`) for the showcase's
  architecture diagrams - they're 9 fixed, hand-designed layouts with
  specific choreographed animations, not a force-directed graph problem.
  `reactflow` sits unused in `frontend/`'s own dependencies for the
  identical reason ("installed if a topology view is ever needed, never
  actually used") - same call applies here.

## Layout

| Path | Purpose |
|---|---|
| `docs/` | Main tool docs - content adapted from the root `README.md`'s Usage/Installation/Security sections, not auto-synced. If the root README changes, these pages need a manual follow-up edit. |
| `sdk/` | A **second, independent** `@docusaurus/plugin-content-docs` instance (`id: 'sdk'`, own `routeBasePath`/`sidebarsSdk.ts`) - not a category nested inside `docs/`. Mirrors `kafkaml-client` being its own independently-packaged directory, and leaves room for independent SDK versioning later without a bigger refactor. |
| `src/components/Showcase/` | The interactive showcase - see its own section below. |
| `src/theme/chartColors.ts` | The Kafka-ML chart palette (5 oklch strings), copied by value from `frontend/src/index.css`'s `--chart-1..5` tokens - a plain copy, not a shared package (this repo's established precedent for 2-consumer assets, e.g. the K-mark logo is also just copied into `static/img/`, not extracted). |
| `src/css/custom.css` | Infima theme variables, same copy-by-value approach for the brand indigo (`oklch(0.511 0.262 276.966)` light / `oklch(0.673 0.182 276.935)` dark, matching `frontend/src/index.css`'s `--primary`). The 7-step Infima shade ladder is generated by stepping oklch's `L` channel at fixed deltas around that base, holding `C`/`H` constant - oklch's `L` is perceptually uniform, so this is a more principled ladder than deriving one from a single hex value with a generic shade-generator tool. |

## The interactive showcase

`src/pages/showcase/index.tsx` renders one client-only page
(`<BrowserOnly>`) hosting `ShowcaseApp.tsx` - a 9-item case switcher (one
per real `CASE` 1-9 from `model_training/tensorflow/utils.py`/
`training.py`, confirmed against the actual dispatch table, not
invented) with three tabs per case: an animated architecture diagram, a
code panel (real model code + real `kafkaml-client` deployment snippet),
and a simulated-metrics results panel.

- `caseDefinitions.ts` is the single source of truth for all 9 cases'
  metadata (model code, SDK snippet, chart config via `MetricsProfile`).
  Semi-supervised learning is a deployment flag (`unsupervised`), not a
  10th case - it gets its own docs page instead of a switcher entry,
  matching the real dispatch table exactly.
- Bounded/classic diagrams (CASE 1, 3) use `useReplayAnimation(active,
  numSteps, stepMs)` - cycles a discrete step index while `active`,
  resets to 0 whenever `active` toggles. `DiagramStage.tsx` forces a full
  remount on every case switch (`key={caseId}`) specifically so this
  reset actually fires.
- Incremental diagrams (CASE 2, 4, and the `incremental` half of 6/8) are
  **not** step-based at all - `useTicker` drives a continuously
  incrementing "batch N" counter with a perpetual flowing-marquee
  connector (`.connectorFlowing`), because incremental training genuinely
  never reaches a "done" state (see `docs/usage/incremental-training.md`)
  and a discrete loop would misrepresent that.
- **Federated diagrams (CASE 5/6/7/8/9) are driven by
  `useAsyncFederation`, not `useReplayAnimation`.** This was a real
  correctness fix, not just a visual one: the first version modeled
  federated rounds as a *synchronized* "all devices train together, all
  report together" cycle, which is wrong. Kafka-ML's actual aggregation
  loop (`model_training/tensorflow/edgeBasedTraining.py` -
  `EdgeBasedTraining`, shared verbatim by CASE 5-8; the near-identical
  `edgeBlockchainBasedTraining.py` for CASE=9) sends the current global
  model, then blocks on `consumer.poll()` (or, for CASE=9,
  `elements_to_aggregate() < 1`) until **the first** device response
  shows up, merges just that one in via pairwise FedAvg, and immediately
  starts the next round - it never waits for the others. Confirmed by
  reading that loop directly, not assumed. `useAsyncFederation` models
  this with each device on its own independent, staggered clock (see its
  own doc comment) - devices visibly finish at different real times, and
  the cloud's "model vN" badge bumps irregularly, only when *some* device
  happens to land, exactly matching the real behavior. `FederatedBaseDiagram`
  covers CASE 5/6/7/8 (parameterized by `incremental`/`distributed`);
  `FederatedBlockchainDiagram` (CASE 9) adds the smart-contract node and
  a per-device ERC-20 reward toast, both driven off the same hook.
- Distributed diagrams (CASE 3/4/7/8) render the father/child pair inside
  a dashed `.chainGroup` container with a `.dataBadge` ("4-dim features")
  that appears on the edge→cloud connector during the handoff - makes
  the hierarchy legible instead of just two boxes in a row. These use two
  explicit stacked `.diagramRow`s (Data Source→chain on row 1, Storage→
  Inference on row 2), not one row left to `flex-wrap` on its own - the
  chain group's padding/border pushes a single row past the panel's
  width at normal viewport sizes, and an unplanned wrap previously
  orphaned the Inference node on its own line.
- `ResultsPanel.tsx`'s chart shape is driven by `MetricsProfile.kind`
  (`'bounded' | 'streaming' | 'federated'`), not one generic
  accuracy/loss line reused everywhere - bounded is a fixed-size reveal
  ("Epoch" x-axis), streaming never stops (scrolling "Batch" window, 🔴
  Live badge), federated points land at *irregular* intervals with a
  "Round N: merged from Device X" caption (matching the same async
  reality `useAsyncFederation` models for the diagrams).
  `distributed: true` renders two side-by-side mini-charts (Edge/Cloud
  submodel) instead of a single chart; `rewards: true` (CASE=9 only)
  adds a per-device cumulative ERC-20 bar chart underneath. `mulberry32`
  (seeded PRNG) keeps each case's curve deterministic per page load, not
  fresh random noise every render - it's illustrative, not a real
  training run, and says so on-screen.

## Gotchas learned the hard way (keep these)

1. **Raw HTML `<img src="/img/...">` does NOT get Docusaurus's
   `baseUrl` prefix - Markdown image syntax (`![]()`) does.** Since this
   site's `baseUrl` is `/kafka-ml-upgraded/` (a GitHub Pages project
   site, not a user/org site at the domain root), an `<img>` tag
   authored as `src="/img/docs/x.png"` resolves to
   `http://host/img/docs/x.png` (missing the base path) while
   `![alt](/img/docs/x.png)` correctly resolves to
   `http://host/kafka-ml-upgraded/img/docs/x.png`. Found by actually
   loading the page and checking `img.naturalWidth === 0` in a headless
   browser, not by reading the rendered HTML (the broken state looks
   like a normal broken-image icon, easy to miss in a quick glance).
   **Every doc image in `docs/usage/*.md` uses Markdown syntax now, on
   purpose** - don't reintroduce raw `<img src="/...">` tags there.
2. **For per-image width control, `<img src={require('@site/static/...').default} width="500" />` works for PNGs but breaks for SVGs.** Docusaurus's webpack/rspack config runs `.svg` imports through `@svgr/webpack` by default, so `require('*.svg').default` returns a **React component function**, not a URL string - passing it as `src` renders the component's stringified source as a literal (broken) URL. Since this repo's doc images are a mix of `.png` and `.svg` (both from the original README's `images/` folder), the working fix was to drop per-image `width` attributes entirely, use plain Markdown syntax everywhere (gotcha #1 above), and cap width globally instead: `.markdown img { max-width: 500px; height: auto; }` in `custom.css`.
3. **Bare `JSX.Element` as a function return type fails `tsc` with `error TS2503: Cannot find namespace 'JSX'`** in this project's TypeScript setup (React 19 + this `tsconfig`), even though the code runs fine in the dev server (Rspack's own transform doesn't do full type-checking). This scaffold's own generated files use `ReactNode` as the return-type annotation instead (see `src/pages/index.tsx`) - every component in `src/components/Showcase/` follows that same convention now. Only caught by actually running `pnpm run typecheck` (== `tsc`), not by the dev server compiling successfully - the dev server and the typecheck script are genuinely different checks here, run both before considering a change done.
4. **pnpm 11's build-script-approval setting isn't read from `package.json` anymore.** `"pnpm": {"onlyBuiltDependencies": [...]}` in `package.json` (the pattern from older pnpm docs/muscle memory) produces a silent `[WARN] ... no longer read by pnpm` and the install still fails with `[ERR_PNPM_IGNORED_BUILDS]`. The actual setting now lives in `pnpm-workspace.yaml`'s `allowBuilds:` map (same file `frontend/`'s `minimumReleaseAgeExclude` list already lives in, for the same "pnpm 11 moved config here" reason) - e.g. `allowBuilds: {'@swc/core': true, core-js: true}`. `@swc/core`/`core-js` need this because `@docusaurus/faster` (this scaffold's default fast-build package) depends on them.
5. **`useLocation` for reading the showcase's `?case=` query param comes from `@docusaurus/router`, not `react-router-dom` directly** - Docusaurus re-exports react-router's hooks through its own package so the site isn't hard-pinned to whatever router major version Docusaurus core happens to use internally.

## Content maintenance

`docs/` is a **manual** adaptation of the root `README.md`, not a
generated mirror - if the README's Usage/Installation/Security sections
change, the corresponding `docs/*.md` page needs its own follow-up edit.
Same for `sdk/*.md` against `kafkaml-client/client.py`'s real method
signatures/docstrings and `backend/app/controllers/deployments.py`'s
`_PASSTHROUGH_FIELDS` list (the source of truth for
`sdk/deployments-and-training-modes.md`'s field table) - re-check both
against the actual code if either changes, don't assume the docs page is
still accurate.

**Never copy `*/CLAUDE.md` content into `docs/`/`sdk/` verbatim** - those
files are AI-assistant-facing (bug logs, internal design rationale,
"draft/PoC" framing addressed to a future maintainer), not user-facing
documentation. Where they contain a true user-relevant fact, rewrite it
in neutral user-facing prose instead of lifting the internal-voice text.
